Organization · Figma

Teams structured by project

Design files are centralized in a single workspace, project by project. A matching structure was set up in SharePoint for document sharing.

03

Organization · Projects

5 core files per project

  1. Project library
  2. Design, for designers
  3. Handoff, for developers
  4. Prototype, for demos
  5. Production, for testers and product owners

This structure also simplifies access rights management.

05

Build · Origin library

How a design system is structured within a project

The table of contents of the Origin library, built for the Ma Gare app on Android and iOS: eight sections, from foundations to page templates, through atoms, molecules and a pre-release test checklist.

06

Origin · Foundations

14 foundations at the core of the library

Colors and design tokens, typography, spacing, corner radius and grids, shadows and focus, icons, pictograms, motion… plus an RGAA/RAAM accessibility kit and a design methodology for documenting outputs.

07

Origin · Page

Timetable page

A page-level component with variants (departures, arrivals, transport modes), linked to the Production file for flows and specifications.

08

Origin · Functional block

Departures/Arrivals board row

A functional block documented with its states (loading, on time, delayed, canceled), its variants by mode, and the list of components it is built from.

09

Design · Designers

A working file co-designed with UX and UI designers

The structure of this file was shaped through conversations with designers about their ideal file.

  • One page per topic, with its status visible in the list: pending UX hub review, abandoned, ready for development.
  • On each page, the design journey from left to right: initial brief, UX recommendations, explored flows.
  • Then the user flow and UX mockups marked “Ready for dev”, and the UI mockups in progress.
10

Handoff · Ready to Dev

A handoff file co-designed with developers

The structure of this file was shaped through conversations with developers about their ideal file.

  • Pages organized by sprint, then by ticket.
  • For each change, a spec sheet: context, prototype, need, purpose of the mockup, impacts, states to handle and validation checklist.
  • Next to it, the annotated mockup, naming every component used.
11

Production · Exploded view

A product overview file co-designed with POs and testers

The structure of this file was shaped through conversations with product owners and testers about their ideal file.

  • A table of contents, a version history, then flows and screens organized by user journey.
  • For each flow, the entry points and use cases of each page (nominal, loading, error…), connected by interactions.
  • A status legend to track the gap with production: to do, inconsistency to fix, OK.
12

Management · Rituals

A shared cadence to keep design teams in sync

  • Monday: design studio stand-up, then DS sync with team champions.
  • Wednesday: steering meeting with the DS project manager.
  • Friday: designer sync to assess upcoming changes.

A tracking file lists every design system component and its status.

13

Communication · Teams

One discussion channel per design system

Dedicated channels let development teams and designers talk directly: a general channel, one for the DS framework, then one per product (Live IHM, Live Socle, Live MaasTransit, Live Multimodal, MaGare).
